# Table — Engineering decisions

Concise record of choices and deviations. Product semantics are settled in the plan; nothing
here reopens UX. Dates are 2026-10-07/08.

| # | Decision | Why / test implication |
|---|---|---|
| D1 | **Workspace:** new isolated local Git repository `/home/user/table` (branch `main`). Not placed in the CFP-Trainer-iOS app or the Financial-Planner-Reasoning-Engine vault, the only repositories attached to the session. | Initial prompt forbids putting Table in the CFP app/vault; no Table repo exists. No remote created or pushed (not authorized). The container is ephemeral — see STATUS for how to preserve. |
| D2 | **Stack (pinned exact):** Node 22.22, TypeScript 5.9.3, Next.js 16.3.8 (App Router, route handlers for all writes), React 19.2.8, PostgreSQL 16.15, `pg` 8.23.1 with hand-written parameterized SQL, `decimal.js` 10.6.0, Better Auth 1.7.7, vitest 5.0.3, Playwright 1.56.1. Next 16.3.8 chosen over 16.4.0 (published the day before bootstrap). TypeScript 7 skipped (new native compiler; Next support unverified). vitest 5 because vitest 4.1.11 triggered an npm arborist peer-resolution crash. | Lockfile committed. |
| D3 | **Migrations:** numbered SQL files in `migrations/`, applied by `src/server/db/migrate.ts`, each in its own transaction, sha256-recorded; an applied file that changes is refused. Better Auth's tables are generated once (`scripts/print-auth-migration.ts`) and committed as `001_auth.sql`. | No ORM; explicit schema is the contract. |
| D4 | **Auth:** Better Auth email+password, sessions in PostgreSQL, **public sign-up disabled**; members provisioned by `npm run member:create` (password via env, never argv). Actor and household are always derived server-side from the session (`src/server/session.ts`). Auth instance built lazily so production config is validated at runtime, not build time. | X01, X11. |
| D5 | **Auth rate limiting is disabled only when `TABLE_ENV=test`.** The browser suite signs two members in per test from 127.0.0.1, which Better Auth's default limiter throttles (3 per window → 429, observed). Production keeps the default limiter. | Environment separation, recorded rather than hidden. |
| D6 | **CSRF/origin:** command routes require `application/json`, reject a mismatched `Origin`/`Sec-Fetch-Site: cross-site`; cookies SameSite (Better Auth default), `Secure` in production. | X01 tests 403/415. |
| D7 | **Concurrency:** every mutation runs in one short transaction that first takes `SELECT … FOR UPDATE` on the household row (orders commits), then validates **per target**: a preview records the revisions of its dependency closure (target night, its cooking event, dependent leftover nights, move destination); Apply rejects if any changed, and also recomputes the operation on current state and requires the reviewed content hash. Whole-week adoption binds to `accepted_choice_revision`. | T08–T12, T22; mutation checks prove a blanket week rule breaks T10 and last-write-wins breaks T08/T11/T22. |
| D8 | **Race tests use database barriers, not sleeps:** the test holds the household row lock, starts command A, waits until `pg_stat_activity` shows it blocked, starts B, waits for 2 waiters, releases. PostgreSQL grants the tuple lock in arrival order. Same mechanism through the browser (clicks) and at the command layer. | Both commit orders for T10, T11, T12, T22, X03. |
| D9 | **Idempotency:** `command_receipts(household, operation_id)` stores request hash + outcome; same id+payload returns the recorded receipt (`replayed: true`); same id + different payload (or actor) is rejected. Rejections are recorded too. Clients generate a new id per user action. | T15, X03. |
| D10 | **Purchase dedup is at the demand level:** approvals are per line fingerprint and exact package count; `StartHandoff` consumes them once and the frozen batch counts as sent, so a second send under a new id sees a changed review fingerprint and is refused. | X03 both orders; mutation "approvals not consumed" is caught. |
| D11 | **Dispatch boundary:** T1 authorize+freeze (lock) → T2 re-validate under lock; superseded → `canceled_before_dispatch` (unchanged lines' approvals re-issued) else commit `dispatch_started` → network call outside any transaction → T3 record outcome. Startup (`src/instrumentation.ts`) marks any leftover `dispatch_started` as `uncertain`; nothing is replayed. Status is an append-only event stream. | T16, T17, X04, X05 (including a real server SIGKILL). |
| D12 | **Fake retailer** is behavior-scripted through `fake_retailer_script` rows and records every request in `fake_retailer_calls` before responding. Barriers (`test_barriers`) only work when `TABLE_ENV=test`. Outcomes are batch-level only, matching the documented Kroger `PUT /v1/cart/add` 204. | No invented per-line results. |
| D13 | **Requirement projection is stored** (`requirement_lines`, `grocery_cycles.projection_summary`) and regenerated inside every command that can affect it, tagged with the accepted revision it was computed from; the snapshot query reads plan + projection in one REPEATABLE READ transaction and refuses a mismatch. | Coherent reads; T13 assertions use persisted rows. |
| D14 | **Quantities** use `decimal.js` (precision 40); units convert only within mass / volume / count; mass oz ≠ fl oz; custom units (can, bunch) match only themselves. Package count = exact ceiling. Money is integer cents. | X06. |
| D15 | **Usual vs extra:** packages = max(meal packages, usual minimum) + explicit extras. Line fingerprint covers demand, requests (not contributor taps), availability observation, product/package, packages needed, order coverage — not "sent" counts, so a frozen batch can be re-validated against current demand. | T18, T13. |
| D16 | **"Not for me"** from either eater excludes a recipe from proposals (dinners are shared); it never deletes the recipe or becomes a medical exclusion. | Plan §1.4. |
| D17 | **Firm budget as a real dependency:** a plan change whose result *definitely* exceeds a firm budget (known prices) is rejected at Apply, so two individually-fitting changes cannot jointly break it. Unknown prices block "Groceries ready" for a firm budget but do not block plan changes. | T22 firm-constraint case; X07. |
| D18 | **Proposal engine:** deterministic ranking (Sounds good +3, Make again +2 per eater, Occasionally +0.5, recent −4, variety adjusts novelty, avoid list for "Different dinners"); hard eligibility first; leftover nights only after leftover-friendly cooks; nights it cannot fill are returned as named open nights. Default 4 cooking sessions when unset, labeled as a default. | Unit tests. |
| D19 | **Updates:** SSE stream polls `change_events` (500 ms) per connection; client refetches the snapshot on any event, on focus/visibility/online, and every 15 s while visible. While hidden or offline, `writesAllowed=false` until a fresh snapshot lands — Apply/Adopt/Send are disabled. Older snapshot responses (lower seq) are ignored. | T08, T09, X02. |
| D20 | **Separate databases** for vitest (`table_test`) and Playwright (`table_e2e`); both are TRUNCATE-reset by the fixture, which refuses any other database name and any `TABLE_ENV` other than `test`. | Prevented a real cross-contamination incident during development. |
| D21 | **Fixed household clock** `TABLE_FIXED_NOW` honored only in `TABLE_ENV=test` (throws otherwise). Next dinner uses the household timezone with a 21:00 local cutoff. | X08, X12. |
| D22 | No CSS framework, no web fonts (system serif/sans), prototype palette as CSS tokens. No recipe photos (letter tile placeholder). | Plan §2. |
| D23 | Leftover-shortfall facts apply from the household's next dinner date at observation time; plates are consumed in night order. | T07. |

## Correction pass after the review of 89f3ea9 (2026-10-08)

| # | Decision | Why / test implication |
|---|---|---|
| D24 | **Whole-week admission** lives in `src/domain/planning/admission.ts` and runs inside `AdoptWeekProposal` before any write: seven nights, none open, a dinner plate for every member on every served night, lunches after their cooking, every plate served by its night, locked nights kept with their cooking, current exclusions on new choices, and a known firm-budget excess on the complete candidate. Unknown prices do not block adoption; they keep grocery readiness/budget unproven. | F01; R-F01a–e. Fact updates and reviewed scoped recoveries may still expose a named unresolved night. |
| D25 | **A lock protects the whole dependency group.** Proposals keep the locked night's cooking and every night that draws from it (with plates and lunches), labeled "Kept — Thursday is locked and shares this cooking". The conservative choice also keeps an unlocked leftover night of a locked source; change it with a scoped edit. | F02; R-F02a/b. |
| D26 | **Released lunches are disclosed, never silently dropped**, and no allocation may precede its cooking after any scoped operation (post-pass blocker). | F02; R-F02c/d. |
| D27 | **Orders reconcile transfers explicitly** (`orders.reconciles_batch_ids`): known contents reconcile every transfer made so far for that pickup; unknown contents reconcile none, so acknowledged/uncertain transfers stay accounted and flagged. Later transfers are always counted. | F04; avoids both forgetting and double-counting. |
| D28 | **Physical supply accounting**: order lines carry the confirmed product and package basis; transfers use their product's basis; requirements compare physical quantities in today's product unit; an unknown basis is counted as today's package and flagged. | F05; R-F05c. |
| D29 | **Substitutions** cover nothing until validated (`ValidateSubstitution`: suitable + amount, or unsuitable). **Corrections** are new receipt observations that supersede one earlier observation (`corrects_id`, unique). No purchasing history row is updated. | F05; R-F05a/b/d. |
| D30 | **"Have enough" carries what was shown** (`reviewed {quantity, unit, fingerprint}`); the server never substitutes its current demand. A changed unit basis is refused for re-review. "Have some" amounts remain explicit facts. | F06; R-F06a both orders. |
| D31 | **Pickup lists are independent of the menu**: capture creates the week/pickup list if needed; after a confirmed order it routes to the next open pickup (up to 8 weeks ahead) and reports the destination. One confirmed order per pickup cycle remains the model. | F07; X09 assertion updated to the corrected destination. |
| D32 | **Remembered staples** (`household_staples`): first usual capture of a known ingredient remembers it (usual quantity default 1, product = current mapping); `rememberUsual` with a quantity sets the usual amount; chips offer one-tap capture. | F07; R-F07c, R-F07-UI. |
| D33 | **Household purchasing revision**: products, mappings, prices, budget and ingredient review bump `households.purchasing_revision` and recompute every cycle in the same transaction; projections record the revision; snapshot and Send refuse a mismatch. Prices are timestamped with the household clock. | F08; R-F08a/b. |
| D34 | **Additional basket cost** = change in `outstandingPurchase` (what still has to be bought after transfers, order and receipts). Pickup spending and dinner ingredient cost stay separate measures. **Received surplus** = received physical quantity beyond plan + requests; suggestions using it rank first and are labeled. | B3. |
| D35 | **Mutation classification** (`tests/mutation/run.mjs`): KILLED requires executed targeted tests and an expected assertion failure; ERROR for runner/compile/DB failures, anchors not found, non-assertion or unexpected failures; clean baseline first; SHA-256 restoration; harness self-test with npx-127 and a no-op control. | V01. |
| D36 | **Verification evidence** is written outside the source tree during the run (`/tmp/table-verify-…`), the tree must be clean, tracked-file hashes are compared before/after, and the evidence is committed afterwards in a separate documentation commit. Bundles include `HEAD` and `main` and are restore-tested both ways. | V01/V02 and handoff §D. |
| D37 | **Layout**: `scroll-padding` reserves the sticky header and fixed nav; the header is opaque. Verified by elementFromPoint at phone width (Chromium). | Screenshot review. |
| D38 | **Git remote**: the owner asked (2026-10-08) to push to a repo under the OpticEggs GitHub account. Creating a repository is refused for this session's GitHub integration (HTTP 403); pushing waits for the owner to create the empty repository and grant access. | Recorded so the next session does not retry blindly. |

## B14 accessibility and B12 remembered staple products (2026-10-08)

| # | Decision | Why / test implication |
|---|---|---|
| D39 | **Change sheet is a hand-built modal, not `<dialog>.showModal()`.** It is portalled to `<body>` and `.app` gets the `inert` attribute while it is open; Escape/Tab are handled at the document (so they work even when the focused control was just removed); a `focusin` guard pulls stray focus back. `showModal()` would make the single live region inert too. | B14-a/b/f. Background unreachable is checked by `focus()` + hit-testing, not by reading attributes. |
| D40 | **One ambient polite live region** (`LiveRegion`, outside `.app`). The currency badge and the grocery delta are no longer live; the stale-preview text is no longer `role=alert`. `useChangeAnnouncer` announces once per change: another member's decision (via the SSE `actor` now carried on change events), a preview of mine that turned stale, approved lines needing review again, offline/back online. Own actions announce their result (Applied, Discarded, Locked). Explicit error alerts stay `role=alert`. Next.js's own route announcer is outside this and only speaks on navigation. | B14-e: refetches and a full poll interval produce zero announcements. |
| D41 | **Focus rules.** Open → selected tab. New preview → its heading, unless the member already moved focus. Apply → sheet closes, focus to the opener. Cancel in the sheet → its selected tab. Close/Escape/backdrop → opener, else that night's Change control, else any Change control, else the week heading — never `<body>`. Remote updates never move focus. | B14-a/b/c/f/g. |
| D42 | **Closing a sheet applies nothing and cancels nothing.** A preview created in the sheet stays an open private draft (listed at the top of the week after closing); unsubmitted inputs are discarded. | B14-a/b. T04's e2e path closes the sheet before locking Thursday (assertions unchanged). |
| D43 | **Remembered staple product = explicit, revision-bound decision** (`ApproveStapleProduct`, `household_staples.product_revision`, append-only `staple_product_decisions`). It is product suitability only: it never creates, consumes or invalidates purchase approvals and never touches requests already captured, transfers or orders. Remembering a usual *quantity* no longer rewrites the product (it used to copy the current mapping). Unknown products and products whose retailer is not the active retailer are refused. | B12a/b/c/d/e/f; 5 mutations. "Approving a different product" in the UI = choose it for this pickup, then "Make this our usual". |
| D44 | **Request product intent** (`household_requests.product_id`). A staple tap (usual or explicit extra) records the remembered product; the projection uses a request's intent ahead of the ingredient mapping, and an intent that is unknown, unavailable, or conflicting leaves the line unresolved — never a silent substitute. Choosing a product for a pickup re-points that pickup's intents (the fingerprint changes, so its approval no longer matches). Availability is "sold by the active retailer"; a retailer switch needs a recompute (purchasing inputs) to take effect in stored projections. | B12b/e. Requests without an intent behave exactly as before (fingerprints unchanged). |
